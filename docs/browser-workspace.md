# Browser workspace

For Docker, start the workspace using the [Docker quick start](../readme.md#docker-quick-start). For a native Python installation, launch the browser editor:

```bash
python3 app.py
```

It opens on `http://127.0.0.1:8765`. Use **Dark mode** in the top bar to switch themes. The editor follows your system appearance initially and remembers your choice in the browser. Use `--port 8766` if that port is in use, or `--no-browser` to open it yourself. Stop the server with Ctrl+C.

Name your **Rollout project** at the top of the workspace. Draft edits autosave after a short pause; wait for **Saved on this computer** before closing the tab. The last project reopens after a refresh or app restart. **New project** starts an empty rollout, **Open project** switches between saved rollouts, and **Save as copy** keeps a separate version. Incomplete drafts can be saved before validation. Sites, VLANs, rollout selections, WAN settings, hidden HA-peer settings, custom DHCP/DNS choices, naming preferences, and the selected site/tab are preserved. Saving or opening a project never starts a deployment.

In Docker, projects are stored in `/data/projects/workspace.sqlite3` in the persistent volume. In a native installation, projects are stored locally in `out/projects/workspace.sqlite3`; stop the app before copying that file for a backup. Use `--data-dir /path/to/folder` for persistent projects, reports, and refreshed UCaaS catalogs, or `--project-dir /path/to/folder` to override only the project directory. Connections, credentials, live lookup caches, and deployment approvals are excluded. If another tab saves the same project, the stale tab keeps its edits and offers **Keep both versions** to save a copy. If the app is unavailable, keep the tab open, start the app, and use **Retry save**. Unsaved changes trigger a browser warning on exit. Tabs opened before autosave was installed still need their drafts exported before refreshing.

**Reference site** is the starting page for a new project. Existing projects reopen their last view. **New branches** opens the full-width rollout overview; choose a branch name to edit its site details and VLANs, then use **Rollout overview** to return. Imported or manually prepared branches remain supported, and references remain excluded from deployment.

The overview checks every draft with the offline validator. **Ready** means local input checks passed, not that tenant resources were verified. **Group by country** uses the Country field (including recognized country codes), is off initially, and is saved with the project. Group checkboxes select eligible branches without changing deployment order. Invalid drafts remain editable; selected invalid drafts can be deselected or inspected through Review. HA branches are labeled **CSV only** and remain blocked from UI deployment.

**Review selected branches** opens the existing offline review. **Preview deployment** then checks the tenant, and deployment still requires explicit approval of the destination. The new overview does not bypass any deployment checks.

The Deployment column shows recorded results for the same project and connected tenant. Successful, existing-site, partial, template-only, and uncertain creation results are excluded from new group selection; inspect the report and tenant before recovery. Records come from final deployment reports written by this version and survive app restarts. Reconnect to the same tenant to see them. Earlier reports and other projects, tenants, CLI runs, or external deployments may show **No recorded result**; that label does not assert that the site is absent. Tenant inventory is checked during preview and again before creation. Recorded completion is not a health check and does not authorize retry or overwrite.

**How to use** is a visible button below the workflow navigation. It opens an optional guide with status explanations, existing-site behavior, and recovery guidance. Close or Escape returns to the current workspace without losing selections.

Choose **Pull reference site**, connect with your tenant API URL and API key, then search for a working site. **Use existing local settings** uses the local `.env` instead (or the file selected with `--env-file`). The key stays on the local server and is not sent back to the browser or included in exports. Manually entered credentials and refreshed tokens are held in memory, not saved.

For App Connector provisioning or LAN application segments, expand **ZPA connection** in the same dialog. Enter the ZPA cloud API URL, client ID, client secret, customer ID, and existing enrollment certificate name (default `Connector`), or use that section's **Use existing local settings** button. Customer ID is optional if supplied by the authentication token. **Check ZPA connection** verifies authentication, customer identity, and certificate lookup without creating resources; it does not verify resource-creation permissions. ZPA is optional when pulling a ZTB reference. Its credentials stay in server memory, are excluded from exports, and are cleared when the app server stops. The current CSV-to-CLI deployment workflow still needs ZPA credentials in the CLI's local credential file; entering them in this editor does not configure the CLI. See [ZPA setup](../ZPA_PROVISIONING_README.md#prerequisites-and-credentials) for required permissions.

Pulling adds an unselected reference with its site settings, private DNS, and VLANs. WAN and HA internal VLANs are excluded from the regular VLAN table; activation WAN settings are imported separately, and loopback VLANs are prepared with `/32` and DHCP off. If the reference contains additional WANs, **Copy additional WANs from reference** is enabled under **Gateways & WAN connectivity**. Review their interfaces and addressing there, or clear the checkbox to omit them. Additional WANs are configured after site creation and stay assigned to their original gateway slot. Choose **Create branches**, set the number of copies, and edit their names and locations in the table. Review each copy’s addressing and select **Include in rollout** when ready. No source-site configuration is changed. The current picker shows up to 100 inventory records and indicates when that limit is reached.

The **Country** field in the site editor and Create branches table has a searchable dropdown with the ZTB portal’s 245 country and territory choices. Click the arrow to browse all countries, or start typing to see matching names and country codes. Click a match or use the arrow keys and Enter to select it; Escape closes the list. You can change the country again while editing a copied site. The picker works in light and dark mode without a tenant connection. CSV files also accept country names, API values such as `THE_NETHERLANDS`, and two-letter codes such as `NL`; unsupported values are flagged during validation.

You can also create sites and VLANs in forms. **CSV templates**, beside Import CSVs, downloads a ZIP with `sites.csv`, two matching VLAN files, and `READ-ME-FIRST.txt` explaining every column. Extract it, replace the example settings, and keep the headers when saving as CSV. Each site row’s `vlans_file` must match its VLAN filename; use unique filenames for separate branch networks. Examples start unselected and optional services are off. **Import CSVs** opens a short guide with a template download and **Choose CSV files**. Choose the sites CSV first, or select all CSV files together. The editor then asks for any referenced VLAN CSVs, which can be selected from another folder. **Load an example rollout** provides placeholder data for exploring the interface.

WAN settings are shown under **Gateways & WAN connectivity**. Choose **Standalone** for one gateway or **High availability** to show Gateway B. New gateway names follow the site name (`<site>-GW`, and `<site>-GW-B` for Gateway B), including edits in the Create branches table. Editing a gateway name directly preserves it as a custom name; imported custom names are preserved. Each gateway has a **DHCP / Static IP** selector; address fields appear only for Static IP. DHCP clears static address fields; Static IP requires an address, mask, and default gateway before export. Existing CSV values determine the initial selection.

**Interface dropdowns** read the selected template's actual ports and roles. WAN choices are specific to Gateway A or B; VLANs offer LAN/management ports and `lo0`, with checkboxes for multiple interfaces. HA link choices use ports assigned that role. Reference assignments stay selected, including custom names and comma-separated lists, and follow branch copies and CSV export. An assignment unavailable for the selected template/role stays visible with a review message. **Enter manually** supports offline work and custom interfaces. Port choices load in the background and are cached per template and connection; opening a dropdown does not call the tenant. Use **Refresh interfaces** after changing a template in the tenant. Changing the template name clears an old template-ID override; an explicit ID override takes precedence otherwise.

Reference imports resolve configured WAN ports from WAN networks matched to each gateway. When a gateway has multiple WAN networks, its primary IP identifies the WAN assignment to preselect; that selection and addressing follow branch copies. Missing or ambiguous assignments remain blank for review instead of falling back to `ge5`. Importing an HA reference still requires review of gateway-specific management VLAN ownership; interface dropdowns do not enable HA UI deployment.

**Template choice** defaults to **Use an existing template**. Choose **Create a template for this site** for an independent copy of the reference site's template. The new template name follows the site name exactly; uncheck **Use site name for template name** for a custom name. The Create branches dialog can select this for every new branch, giving each one its own name. Interface dropdowns still use the source template's ports. Site-level WAN/VLAN edits remain in the branch configuration; this action clones the reference template, not live site overrides into a template.

Review and preview show the planned template creation without creating resources. On deployment, the engine checks the name and source configuration, calls the native template-clone API with the new name, resolves and verifies the new template ID, and only then deploys the site using that ID. An existing name or failed/unverified clone blocks that site's creation. Source-template changes invalidate the preview. Template IDs and outcomes appear in the run report. If cloning succeeds but site creation fails, inspect the tenant and use the verified template as an existing template for recovery after checking the site; do not blindly clone or deploy again. Native template-clone creation has been verified during the standalone test deployment.

For ZIA locations, new branch copies default to **Create a new location**, with **Use site name for location name** checked. A source set to **No ZIA location** keeps that choice in its copies. The branch builder explains this before you create copies; each location is created only when you deploy. The location name stays in sync as you rename a branch; uncheck the naming checkbox for a custom name. **Use an existing location** requires a matching location. **Use existing if found, otherwise create** (the CSV value `auto`) reuses a matching location or creates one if absent. Help beneath the selector explains the selected action using the current name. Location-template fields appear only for choices that can create a new location. Imported settings and custom names are preserved until you change them; creating branch copies does not change the source. CSV exports contain the selected mode and resulting name, with no additional columns.

All VLAN settings are shown directly in the editor. When enabling **On / Inherit** or **Non-airgapped** DHCP, **Automatic** range starts after the gateway and ends at the subnet’s last usable address. It updates when the gateway or mask changes. Choose **Custom** to enter a narrower range or reserve addresses for static devices. Pulled and imported DHCP-enabled VLANs default to Automatic, replacing source ranges with calculated endpoints. Choose Custom for a narrower range. Custom choices follow branch copies within the editor; reopening CSVs defaults to Automatic again. Exported CSVs contain explicit endpoints, not an automatic-mode flag. With DHCP off, scope cells are ignored during validation and excluded from deployment; editor exports leave them blank.

Each DHCP-enabled VLAN also has a **DNS source** and **DNS servers** field. With **VLAN gateway (automatic)**, DNS uses that VLAN's gateway IP and follows gateway edits, branch copies, and bulk address changes. New VLANs and imports without explicit DNS default to this option; an imported DNS value equal to the gateway also follows it. Other explicit DNS values remain **Custom**. Choose Custom for external resolvers or a comma-separated list. UI exports carry the resolved addresses in optional `per_network_dns`; older CSVs without that field retain the site WAN DNS fallback. Reference exports preserve explicit per-VLAN DNS. This sets the network API field; actual client DNS assignment still needs appliance/DHCP verification.

Management networks can be selected for the same disabled ZPA application segment. A management loopback on `lo0` contributes its exact `/32` host, with DHCP off. Branch copies preserve the reference management IP: set the intended branch address before publishing it. The VLAN editor points to App Connector provisioning when it is off; tenant preview names the exact destinations and existing ZPA segments that overlap. A conflict leaves existing segments unchanged.

For VLANs that share an address pattern, use the optional **Change addressing** button on the VLAN page. Enter matching prefixes (for example, `10.20` → `10.30`), select VLANs, and review gateway and DHCP changes before applying. Automatic ranges recalculate; Custom ranges retain their host endpoints when they match the prefix. DHCP-off ranges stay empty. Management VLANs require explicit selection; WAN/HA networks and site-level WAN/DNS settings are excluded. Invalid ranges and overlapping destination VLAN networks block Apply. The action only edits existing fields in the current site: there are no new CSV columns or Python deployment options. Unrelated VLANs can still be edited individually.

**Include in ZPA segment** works for LAN and management VLANs, including `lo0`. Select it on the management row to include its exact `/32` in the same disabled segment. CSV deployments use `zpa_include=1` on that row. A pending loopback binding is reported separately and does not block segment staging; actual VLAN or App Connector failures still do.

Optional **UCaaS local breakout** creates two shared site forwarding rules—Web Breakout and Media Breakout—for selected Teams, Zoom Meetings, Webex and Google Meet destinations. It defaults off, uses reusable IPv4, domain and Port objects, checks existing SaaS and destination/Port objects before creating anything, follows the selected primary WAN, and infers the other WAN. Path selection defaults to **Best**, with **None** and **Balanced** also available. Preview shows combined destination/protocol/port sets and planned object reuse/creation; all selected vendor port coverage is retained. See [UCaaS local breakout](ucaas-local-breakout.md) for scope, refresh, CSV fields and verification limits.

Optional **Use private DNS only for selected domains** adds a private-domain rule below ZPA and immediately above the automatic catch-all, then changes that catch-all to WAN DNS. It reuses exact domain objects, verifies site resolver memberships and keeps the automatic Zscaler and ZPA rules unchanged. Off by default; new-site deployment only. See [Private-domain DNS](private-domain-dns.md) for preview, CSV and recovery behavior.

Use **Validate & review** for offline input checks, then **Preview deployment** to check tenant templates, locations, existing sites, and requested ZPA resources. Use **Connections** on the Review page if you have not connected yet. UI deployment uses the ZTB connection and any separately configured ZPA connection; ZPA settings from a saved ZTB connection are also available for preflight. No resource-creation requests occur during preview.

After preview succeeds, review the destination tenant, ZPA customer when applicable, selected sites, and planned resources. Click **Deploy N sites** and confirm the destination. The app rechecks tenant references and duplicates before creation. Edits, connection changes, or a preview older than five minutes require a new preview. Failed checks block the rollout. UI deployment currently blocks HA sites until the WAN and management reference mappings are verified.

Progress and per-site outcomes appear on the same Review page. **Download report** saves the short summary; JSON and text reports are also stored under `out/runs/` natively, or `/data/runs/` in Docker. Keep the local app running during deployment. If the native workspace receives Ctrl+C or POSIX SIGHUP, it stops serving the browser and waits for the active deployment batch to finish and save its report; repeated interrupts keep waiting. Forced termination can still leave an incomplete run. Preview results are not saved across app restarts. Refreshing the browser restores the saved draft and reconnects to the latest run. Restarting the app restores drafts, but does not resume interrupted deployments: inspect the tenant and report before recovery. Reopened drafts require a fresh preview before deployment. The server accepts one run at a time and consumes each deployment approval once; separate app/CLI processes are not coordinated. There is no automatic retry or rollback for partial deployments.

Each newly created site also gets **View diagram** and **Download site diagram** actions for PNG, SVG, editable Visio, and a ZIP containing all three. **Saved deployment diagrams** retains earlier runs for the current project and offers a ZIP download. Optional switch/ISP labels and an offline planned preview are under **Site details → Diagram details**. Diagram capture uses read-only configuration checks; failures are documentation warnings and do not repeat deployment. See [Site diagrams](site-diagrams.md) for configuration status labels, HA wiring, persistence, and import verification limits.

For the optional Python workflow, choose **Download CSV bundle**. Extract the ZIP and pass its `sites.csv` to the [CLI preview](cli.md#3-validate-and-preview). Each site references a file in the included `vlans/` folder. Non-credential columns not exposed in the forms are preserved during export. Imports reject credential fields, including fields inside JSON cells; exports filter them from older drafts. Formula-like CSV headers or values block export rather than silently changing configuration names.

The workspace does not overwrite source CSVs. Saved projects preserve drafts on this computer; CSV export provides a portable copy. Standalone API staging has been tested, including template cloning, ZIA/ZPA configuration, UCaaS Best-path rules, and private-domain DNS order. This does not establish appliance activation or live traffic behavior. HA staging has partial API coverage, but UI HA deployment remains gated. Management loopback binding remains unresolved on pending appliances. A native desktop installer remains future work; Docker packaging is available.
